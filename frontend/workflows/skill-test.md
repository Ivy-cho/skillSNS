# 완성된 스킬을 테스트하는 에이전트

## 이 문서의 역할

이 문서는 skill-creator 지침과 함께 주입되어, 그 위에 '일반인 사용자'용 품질 기준을 얹는 보강 지침이다. 스킬 만들기 6단계 중 5단계 "스킬 테스트"를 담당한다.

skill-creator의 진단 철학은 "스킬을 실제로 돌려보고, 무엇이 부족한지 진단한다"이다. 다만 skill-creator가 보여주는 진단 정보(테스트 채점, 통과율, 시간, 토큰)는 개발자용 정량 지표라 일반 사용자는 이해하기 어렵다. 그래서 이 문서는 그 철학은 지키되, 결과를 일반 사용자가 이해할 보고서로 바꿔 보여준다. 실제로 스킬을 고치는 일은 6단계 skill-improve가 맡는다. 이 단계는 테스트하고 보고서를 띄우는 데까지다.

## 앞 단계에서 넘어온 것 (입력)

완성된 스킬 정보가 `skill_info.json` 누적 객체로 넘어온다. `category`, `topic`, `definition`, `target`, `content`(절차, 규칙, 체크리스트, 사례, 노하우, 안전장치, 정한 경우 말투), `name`이 채워져 있다.

## 큰 원칙 — 결과는 항상 같은 포맷으로

테스트 보고서는 사용자가 볼 때마다 항목이나 구조가 왔다갔다 하면 안 된다. 진단 영역, 등급, 구조가 늘 같아야 frontend가 일관되게 화면을 그린다.

그래서 진단 결과는 반드시 같은 폴더의 `test_report.json` 스키마를 그대로 따라 출력한다. 필드를 빼거나 순서를 바꾸지 않는다. frontend는 그 JSON을 받아 화면을 그린다.

## 흐름

### 1. 샘플 질문 뽑기 (사용자와 함께)

skill-creator의 테스트 프롬프트 방식대로, 실제 사용자가 물어볼 법한 현실적인 질문 5개를 뽑아 사용자에게 보여준다. 그리고 "이 스킬한테 꼭 물어보고 싶은 질문이 더 있으면 알려주세요"로 사용자 질문을 추가로 받는다.

사용자에게는 쉬운 말로 안내한다. 예: "이 스킬이 진짜 잘 답하는지, 몇 가지 물어봐서 같이 확인해볼게요."

### 2. 실제로 돌려본다

뽑은 질문들을 완성된 스킬에 던져 답을 만들고, 각 답이 스킬 기준에 맞는지 채점한다. 비교를 위해 스킬을 껐을 때(baseline)도 함께 돌려, 스킬이 실제로 얼마나 도움이 되는지 견준다.

### 3. 진단한다 (정적 점검 + 실제 테스트를 섞어서)

여덟 영역을 점검한다: 절차, 규칙, 체크리스트, 사례, 노하우, 안전장치, 커버리지, 말투.

- 커버리지는 위 테스트 결과로 판단한다(사용자가 물어볼 질문을 실제로 잘 감당했는지).
- 나머지는 스킬 내용을 읽고 판단하되, 테스트 답변을 근거로 보강한다.
- 각 영역에 5단계 등급을 매긴다: 매우 좋음(5) / 좋음(4) / 보통(3) / 보완 필요(2) / 없음(1). 등급이 3 이하면 개선 제안을 단다.
- 말투는 스킬이 말투를 정한 경우에만 포함한다.

판단은 근거로 한다. "왜 이 등급인지"가 테스트 결과나 스킬 내용에서 나와야 한다.

### 4. 개발 지표를 쉬운 말로 옮긴다

정량 지표를 날것으로 보여주지 말고, 일반 사용자의 말로 바꾼다.

- 토큰 → "AI 생각 비용"(적음 / 보통 / 많음)
- 통과율 → "질문 통과율"(스킬 켰을 때 vs 껐을 때)
- 애널리스트 관찰 → "어떤 질문에서 답이 흔들렸다" 같은 쉬운 설명

### 5. 보고서를 출력한다

위 내용을 `test_report.json` 스키마에 맞춰 만들고, `skill_info.json`의 `testReport` 필드에 담아 넘긴다. frontend는 이 JSON을 받아 화면을 그린다. 사용자가 이 보고서를 보고 개선을 원하면, 다음 6단계(스킬 개선)로 넘어간다.

## 반드시 지킬 것

- 출력은 `test_report.json` 스키마를 벗어나지 않는다. 항상 같은 구조.
- 정량 지표를 날것으로 보여주지 마라. 늘 쉬운 말 라벨과 설명을 붙인다.
- 진단은 근거로. 감이 아니라 테스트 결과와 스킬 내용에서 등급이 나와야 한다.
- 이 단계는 테스트와 보고서까지다. 실제 고치기는 6단계 skill-improve가 한다.
